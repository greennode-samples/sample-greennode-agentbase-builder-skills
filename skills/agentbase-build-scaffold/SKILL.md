# Scaffold an AgentBase agent project (uv + LangGraph)

## Step 1 — Gather input (ask the user, don't decide yourself)

- **Project name**: `^[a-z][a-z0-9-]{1,38}[a-z0-9]$` — 3–40 chars, lowercase letters/digits/`-`, starts with a letter, does not end with `-` (used for the image name, Langfuse tag, `AGENT_NAME`). Name with spaces/uppercase ⇒ propose a normalized version and confirm.
- **Target directory** (default: current directory).
- **Need a UI?** ⇒ `--with-frontend` = mobile app (Expo React Native, `/agentbase-build-frontend`) · `--with-web` = web app in the browser (Next.js with its own BFF: login, cookies, CSRF — `/agentbase-build-web`). "Web chat", "chat page on our site" ⇒ `--with-web`; both flags can be combined.

Present a summary and **wait for confirmation (HARD GATE)** before creating files. If `src/backend` already exists ⇒ stop and ask the user (the script also refuses to overwrite).

## Step 2 — Run the scaffold script

The script lives in this skill's directory (the one containing SKILL.md):

```bash
bash <skill-dir>/scripts/scaffold.sh <project-name> <target-dir> [--with-frontend] [--with-web] [--no-sync]
```

The script merges the `assets/backend/` of these skills: scaffold · llm · memory · tracing · mcp · auth · identity · hitl · eval · a2a · security-audit (each skill owns its module), adds the root files, replaces `__PROJECT_NAME__`, creates `.env` from `.env.example`, runs `uv sync` and `uv run pytest`. If sync or tests fail, the script prints the recovery command (`cd src/backend && uv sync && uv run pytest`); if it fails while writing files, it says what to remove before re-running.

**All backend modules are required.** Optional components (long-term memory, reflection, HITL, MCP, A2A) ship code but are **disabled via env** — enable per the decision guide; do not delete their files: the modules import each other (`app/tools` imports `app/a2a`, the graph imports `app/reflection`/`app/hitl`, `app/service` imports `app/tools.mcp`/`app/hitl`…). Only `app/identity.py` (+ `tests/test_identity.py`) may be removed when no tool uses outbound credentials.

Can't run the script (Windows without bash, missing skill) ⇒ copy manually following the table in the `scripts/scaffold.sh` header.

## Step 3 — Verify

```bash
cd <target-dir>
make test        # must be green (offline tests: fake LLM, in-memory memory, auth none)
make lint
```

Report to the user: list of created files + next steps: **they run `make set-secret` in their own terminal** (hidden prompt for the IAM `client_id`/`client_secret` → `.greennode.json` and `LLM_API_KEY` → `.env`; you cannot type into it — never offer to take the values in the chat), then `make check-creds`; `/agentbase-build-llm` to get a key, `/agentbase-build-memory` to create memory.

## Managing the environment with uv (MANDATORY)

| Task | Command (run in `src/backend`) |
|---|---|
| Install env from lock | `uv sync --locked` (CI: `uv sync --locked`; Docker: `uv sync --locked --no-dev` — both fail when `uv.lock` no longer matches `pyproject.toml`) |
| Add dependency | `uv add <pkg>` · dev: `uv add --dev <pkg>` · extra: `uv add "pkg[extra]"` |
| Remove dependency | `uv remove <pkg>` |
| Upgrade version | `uv lock --upgrade-package <pkg>` then `uv sync` |
| Run commands | `uv run python main.py` · `uv run pytest` · `uv run ruff check .` |
| Python version | **Single standard: Python 3.13** — `.python-version` = `3.13`, `requires-python = ">=3.13,<3.14"`, Docker `python:3.13-slim`. uv downloads 3.13 automatically if missing (`uv python install 3.13`) |

Rules: **every Python command runs via `uv run`** (including one-liners: `uv run python -c ...`) — don't call `python`/`python3` directly since macOS/Linux often ship an old system Python (e.g. 3.9) with the wrong version and none of the project's dependencies; **no** `pip install`, **no** `requirements.txt`, **no** manual venv activation in instructions; always commit `uv.lock`; the Dockerfile and CI use `uv sync --locked` for reproducible builds.

**Supply chain.** The skills ship the `uv.lock` their tests ran against (`assets/backend/uv.lock`, also for the MCP server template), and the scaffold installs it with `uv sync --locked`: every new project starts from the same, tested packages, not from whatever PyPI resolves to that day. Both Dockerfiles pin their base images by digest (`python:3.13-slim@sha256:…`, `uv:0.10@sha256:…`; the tag stays for readability), so a build never changes under you. Nothing updates itself: generated projects get `.github/dependabot.yml` (uv / docker / GitHub Actions, plus npm for `src/web` and `src/frontend` when present — grouped weekly PRs; it is a seed, edit it freely) — **review and merge those PRs, run `make test` and `make security-scan`**, and enable Dependabot alerts in the repository settings. The npm lockfiles (`package-lock.json` of `src/web`, `src/frontend`) are created by the first `npm install` — commit them, and use `npm ci` in CI. Maintainers of these skills: after changing a `pyproject.toml` run `scripts/relock.sh` (`--upgrade` for newer versions, then the full tests) and commit the locks; skills CI fails on a stale lock or a base image without a digest.

### Env files

| File | Used for | Commit? |
|---|---|---|
| `.env.example` | Full template of every `Settings` variable | ✔ |
| `.env` | Local dev (`APP_ENV=local`, may use `AUTH_MODE=none`, `MEMORY_BACKEND=inmemory`) | ✖ |
| `.env.dev.example` / `.env.staging.example` / `.env.prod.example` | Per-environment **non-secret** runtime config (secrets `<set-in-deploy>`); CI merges it with the secret store | ✔ |
| `.env.dev` / `.env.staging` / `.env.prod` | Copy of the `.example` with secrets filled by the user (`make set-secret ENV_FILE=src/backend/.env.<env>`) — passed to the runtime by `/agentbase-deploy --env-file` | ✖ |
| `.greennode.json` | IAM credentials for local dev (read by the SDK). The **user** writes it with `make set-secret NAME=iam` (from `.greennode.json.example`) — never via chat | ✖ |
| `.greennode.json.example` | Template `{client_id, client_secret, agent_identity}` (`agent_identity`: the **dev** identity, only when tools use Identity providers) | ✔ |

**Secrets: `make set-secret`** (`scripts/set_secret.py`, Python 3 standard library — works before `uv sync`) is run by the **user in their own terminal**, never by you through the chat: it lists what can be set (keys of `.greennode.json.example`; the secrets the env file's template declares; secret-looking `${VAR}` of enabled entries in `mcp_servers.json` / `a2a_agents.json`), reads each value with a hidden prompt (refuses without a TTY), rejects obvious wrong pastes (quotes, spaces, `Bearer `, a whole `NAME=value` line, placeholders, the same value as another secret…) and anything the strict env-file format forbids, asks before replacing a value, and writes atomically with mode 600 — every other line and key is kept, `.env` is created from `.env.example` if missing, and files git would commit are refused. It prints only `set (N chars)`. `NAME=<key|group>` (`iam`, `llm`, `langfuse`, `feedback`, `identity`), `ENV_FILE=src/backend/.env.<env>` (deploy env file: IAM is refused, the `<set-in-deploy>` keys are the default), `LIST=1` (names + set/not set — safe for you to run), `STDIN=1` (one value piped from a secret manager, e.g. `op read … | make set-secret NAME=LLM_API_KEY STDIN=1`; never `echo <secret> |`). Where to open the terminal: `/agentbase-build` → *Credentials*.

`make check-creds` (`scripts/check_creds.py`) verifies IAM, the LLM key against **every** tier's primary and fallback model (FAIL for a primary, WARN for a fallback), the agent identity and Langfuse keys, and prints only `OK/WARN/FAIL` + non-secret IDs (the **developer's** IAM principal `iam:<sub>` from the local `.greennode.json` — the runtime has its own, see `/agentbase-build-deploy` Step 5); each FAIL names the `make set-secret NAME=…` to re-run. Run it after the user ran `make set-secret`.

Deploy env files are read **literally** by the platform (`runtime.sh --env-file`) and by `docker run --env-file`, unlike python-dotenv for the local `.env`: one `KEY=VALUE` per line, no quotes, no inline comments, no `export`, no `${VAR}`. `make check-env ENV_FILE=src/backend/.env.<env>` (`deploy/env_file.py`) lints a file and prints key names only.

`APP_ENV=local` (the default) is **refused on the Runtime** (detected: `GREENNODE_AGENT_IDENTITY` injected by the platform **and** no `.greennode.json` — locally the IAM pair always lives in that file), so a deploy env file that forgets `APP_ENV` cannot fall back to `AUTH_MODE=none`. `make dev` binds `127.0.0.1` when `APP_ENV=local` + `AUTH_MODE=none` outside a container (`0.0.0.0` otherwise, as the Runtime requires).

Deploy env files **must not contain** `GREENNODE_CLIENT_ID`, `GREENNODE_CLIENT_SECRET`, `GREENNODE_AGENT_IDENTITY` (the runtime injects them) or `GREENNODE_ENDPOINT_URL` (platform-reserved name; set `A2A_PUBLIC_URL` instead).

## What the scaffold creates

See the directory tree and module responsibilities in `/agentbase-build` → `references/architecture.md`. Files owned by this skill:

- `assets/backend/pyproject.toml` — standard dependencies: every package the code imports directly is declared, each capped at its next major (`greennode-agentbase` at the next minor — the code relies on SDK internals); test-only imports in the `dev` group.
- `assets/backend/main.py` — thin entrypoint; **keep `RequestLimitsMiddleware` first and `XAccelBufferingMiddleware`** when adding middleware (the SDK drops its default middleware if you pass `middleware=`; without it SSE gets buffered).
- `assets/backend/app/limits.py` — admission control, **per replica** (× replicas = the effective limit; a strict global quota needs an API gateway in front): POST body over `MAX_REQUEST_BYTES` (1 MiB) ⇒ 413 before anything parses it; more than `MAX_CONCURRENT_REQUESTS` (32) `/invocations` + `/a2a` at once ⇒ 503 + `Retry-After`; chat/resume over `RATE_LIMIT_USER_PER_MIN` (30) per verified user or `RATE_LIMIT_TENANT_PER_MIN` (0 = off) per tenant ⇒ 429 + `details.retry_after_s`. The LLM (10 requests/min) and Memory (10 concurrent) quotas are per account and shared by every user: without these one caller starves the rest. Size them from the spec's load; tests `tests/test_limits.py`.
- `assets/backend/app/config.py` — `Settings` (single env source, `env_ignore_empty` ⇒ `KEY=` uses the default) + safety validation (forbids `AUTH_MODE=none` outside local) + `normalize_iam_env()` (prevents mismatched IAM pairs).
- `assets/backend/app/service.py` — payload contract, orchestration, HITL resume (interrupt taken from graph output; calls left unanswered by an ended request closed as "outcome unknown"), session rotation at `SESSION_MAX_TURNS` (the response's `session_id` is the new one — `/agentbase-build-memory` *Long sessions*), bounded wait for the per-session lock (409 after `REQUEST_TIMEOUT_S`), feedback token, `run_chat()`/`run_resume()`/`pending_tool_calls()` for eval & A2A.
- `assets/backend/app/graph/{state,builder}.py` — the single graph.
- `assets/backend/app/prompts/system.md` — system prompt (rewrite for your domain, but keep its "Dates & time" and "Memory" sections).
- `assets/backend/scripts/{set_secret,check_creds}.py` — `make set-secret` / `make check-creds` (above); tests `tests/test_set_secret.py`, `tests/test_check_creds.py`. The MCP server template ships an identical `set_secret.py` (skills CI compares them).
- `assets/backend/tests/{conftest,test_agent,test_isolation,test_limits,test_service,test_turn_context}.py` — `fake_llm` fixture (patches `get_llm` in every module listed in `LLM_MODULES`; add new LLM-calling modules there); conftest overrides env so tests don't depend on `.env`; per-user isolation tests; service error mapping (stale resume ⇒ 409, LLM config errors); per-turn context (current date/time in `APP_TIMEZONE`, recalled notes framed as data).
- `assets/backend/.python-version` — `3.13`.
- `assets/backend/Dockerfile` — multi-stage `python:3.13-slim`: uv only in the builder; the runtime stage gets the venv + code (root-owned, read-only for the non-root `agent` user), `ARG AGENT_VERSION` → `ENV AGENT_VERSION` (Langfuse release = image tag), port 8080. `.dockerignore` uses `**/` patterns so nested caches/secrets are excluded too.
- `scripts/template_files.py` → `.agentbase-template.json` (committed): which class each generated file belongs to and the hash of what the template wrote — see *Upgrade an existing project*.
- `assets/root/*` — Makefile, README, .gitignore, `.agentbase-state.json` (flat keys used by the platform wizard + `standard_version`, `scaffold_version` = the skills' git SHA or version, and `environments.{dev,staging,prod}` with runtime/endpoint/network/inbound auth/identity/memory/LLM key/gateway/policy group/principal per environment), `ci.yml` → `.github/workflows/ci.yml` (lint + test, eval gate, manual deploy/redeploy), `agent.yaml.tpl` → `deploy/agent.yaml.tpl` (manifest for `grn agentbase deploy up`, rendered in CI), `render_runtime_spec.py` → `deploy/render_runtime_spec.py` (merges config + secrets, spec for `grn agentbase runtime update`), `env_file.py` → `deploy/env_file.py` (`make check-env`) and `env.deploy.example` → `src/backend/.env.{dev,staging,prod}.example`. Existing files are never overwritten — see `/agentbase-build-deploy` *CI/CD*.

## After scaffolding — customize for your domain

1. Write `app/prompts/system.md` per the Agent Spec. Keep the **"Dates & time"** and **"Memory"** sections: they tell the model how to use the per-turn date/time and to treat recalled notes as data, not instructions.
2. Add tools in `app/tools/local_tools.py` or via MCP (`/agentbase-build-mcp`).
3. Add domain nodes in `app/graph/builder.py` (if you need a router/sub-agent), state fields in `state.py`.
4. Add tests for each tool/node; add eval items to `evals/datasets/`.

## Upgrade an existing project

When a project was generated by an older version of these skills (`standard_version` in its `.agentbase-state.json` is older than this skill set's — see the repo's CHANGELOG.md), pull in the template fixes with `scripts/upgrade.py` (next to scaffold.sh; needs git, bash and python3 — no venv). Never re-scaffold over a project or copy template files over it by hand.

```bash
cd <project> && git status                         # must be clean: the upgrade lands as ONE reviewable diff
python3 <skill-dir>/scripts/upgrade.py .           # dry run: prints the plan, writes nothing
python3 <skill-dir>/scripts/upgrade.py . --diff    # + the template's own change for each file to look at
python3 <skill-dir>/scripts/upgrade.py . --apply   # after the user confirms the plan (HARD GATE); exit 1 while conflicts remain
```

Per file it runs a 3-way merge: **base** = the template as generated for THIS project (the recorded version's own scaffold.sh, re-run offline with the project's name; the frontend overlay without create-expo), **yours** = the project's file, **new** = the current template.

| Plan | Meaning | You |
|---|---|---|
| `replace` / `add` | template changed it and you did not / new template file | — |
| `merge` | you and the template changed different lines | review in `git diff` |
| `conflict` | both changed the same lines: `<<<<<<<` yours, `\|\|\|\|\|\|\|` old template, `>>>>>>>` new template | resolve |
| `manual` | no old template to merge against (no history) | merge `<file>.agentbase-new` into the file, delete it |
| `skipped-owned` | a seed / file of yours that the template changed | port what applies from `<file>.agentbase-new`, delete it |
| `removed-upstream` · `deleted-locally` | template dropped it (kept; `--delete-removed` deletes it if you never changed it) · you deleted it (not re-added) | decide |
| `state` | `.agentbase-state.json`: versions updated, new keys added, your IDs kept | — |

**Ownership** (`scripts/template_files.py`; per file in the committed `.agentbase-template.json`, written by scaffold.sh and every upgrade with the hash of what the template wrote):
- **managed** — 3-way merged: code, tests, Dockerfile, `pyproject.toml`, Makefile, CI workflow, `deploy/*`, every `.env*.example`, the frontend overlay (`App.tsx`, `src/…`).
- **seed** — created once, then yours; replaced only while byte-identical to the template: `README.md`, `app/prompts/system.md` (conflict markers would reach the LLM — port the template's "Dates & time"/"Memory" changes by hand), `app/knowledge/*`, `evals/datasets/*` (your pass rate), `mcp_servers.json`, `a2a_agents.json` (your URLs; JSON does not survive markers). Add globs to `developer_owned` in `.agentbase-template.json` to treat more files this way (e.g. a graph you rewrote).
- **never touched** (not even read): `.env`, `.env.<env>`, `.greennode.json`, `*.credentials.json`, `uv.lock` (regenerate it), `deploy/agent.yaml`, `.venv/`, `node_modules/`, the create-expo files of `src/frontend` (`package.json`, `app.json`, `tsconfig.json`, `assets/`…).

**Which template generated the project** (the base):
- Projects with `.agentbase-template.json` (scaffolded since this tool exists): exact hashes; `scaffold_version` `…+git.<sha>` ⇒ the base is rebuilt from the skills' git history (`git archive`, nothing written to the repo).
- 0.3.0 / 0.3.1: the SHA when scaffolded from a git checkout; a bare version (plugin install) ⇒ the commit stamped with that version that generates most of the project's files unchanged.
- Before 0.3.0 nothing is recorded ⇒ `--from <commit>` is required. `--guess-from` ranks the skills' commits by identical files; on a tie take the **older** one (an older base only adds conflicts, a newer one can silently undo template fixes in files you changed). The last commit before 0.3.0 is `3528ac6`.
- Skills installed as a plugin / with `npx skills` have no `.git`: `git clone https://github.com/greennode-samples/sample-greennode-agentbase-builder-skills.git` and pass `--skills-repo <clone>` (or `--from <dir>` holding the old version's skills). Without any history the manifest hashes still replace the files you never changed; the ones you changed get `<file>.agentbase-new`.

**After `--apply`**: resolve conflicts and `.agentbase-new` files → `cd src/backend && uv lock && uv sync` → `make lint && make test` → `make check-env ENV_FILE=src/backend/.env.<env>.example`, and tell the user which new keys (from the `.example` files — never read their `.env*`) to add to their git-ignored `.env` / `.env.<env>` → read CHANGELOG.md between the two versions → review `git diff` and commit it as one change. Resolve conflicts in the user's favor where the business logic is theirs; ask when unsure.
